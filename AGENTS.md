# TurboIDE: проверка и тестирование

Эти инструкции нужны агентам и разработчикам, которые меняют сборку, терминальный UI, запуск программ или отладчик. Ручные сценарии выполняйте в отдельном проекте в `%TEMP%`, чтобы не менять пользовательские `.prj`, `.dsk` и исходники.

## Сборка и быстрые проверки

В PowerShell из корня TurboIDE:

```powershell
cmake -S . -B .build/agent-test -G "Visual Studio 17 2022" -A x64 -DTURBOIDE_BUILD_TESTS=ON
cmake --build .build/agent-test --config Release --target turboide gdb_mi_self_check run_interrupt_test
& .\.build\agent-test\Release\gdb_mi_self_check.exe
& .\.build\agent-test\Release\run_interrupt_test.exe
```

Успешный запуск self-check программ завершается с кодом `0`. Если сборочная папка уже настроена другим генератором, используйте новую папку, например `.build/agent-test-vs`, вместо повторного configure. Для GCC-компиляции исходников IDE нужен MinGW-w64 `gcc.exe` в `PATH` или заданный `TURBOIDE_GCC`; для отладки нужен `gdb.exe` в `PATH` или заданный `TURBOIDE_GDB`.

## Обязательная проверка UI через Scanline Term MCP

Перед сценарием загрузите skill `$scanline-term-mcp`. Проверяйте терминальный UI через MCP-owned вкладку Scanline Term. Он воспроизводимо передаёт клавиши и возвращает текст экрана вместе с `screen.styles`, поэтому проверяет не только наличие элемента, но и его реальные атрибуты цвета. До начала включите **MCP terminal mode** в Scanline Term и настройте в Codex sidecar `scanline-term-mcp.exe` той же сборки, что и запущенное приложение.

Создайте вкладку с `turboide.exe`, явным `cwd` в отдельной папке `%TEMP%` и достаточным размером, например `120×40`. После каждого действия считывайте экран через `observe_terminal`; для TUI используйте именованные клавиши, а не координаты из старого снимка. В конце закрывайте только созданную MCP-вкладку через её opaque handle.

В отдельной папке создайте и откройте в TurboIDE сохранённый файл `watch.c`:

```c
int main(void) {
    int i = 40;
    i++;
    i += 2;
    return i;
}
```

Поставьте breakpoint на `i++`, добавьте Watch `i` через **Debug → Add Watch** или `Ctrl+F7`, затем проверьте:

1. **Debug → Start debugging** собирает файл с символами и запускает сессию. При остановке на `i++` значение Watch равно `40`, а исходник переходит к правильной строке.
2. Breakpoint виден после установки, снимается одним переключением и снова устанавливается; проверьте и `Ctrl+F8`, и пункт меню. Первичная остановка GDB на `main` сама по себе не должна выглядеть как оставшийся пользовательский breakpoint.
3. **Trace (F7)** выполняет `i++`, Watch показывает `41`; **Step (F8)** выполняет `i += 2`, Watch показывает `43`; **Continue (F4)** завершает программу. Маркер текущей строки и breakpoint отображаются корректно во время сессии.
4. Watches имеют классический синий фон FPC/Turbo Vision и читаемый светлый текст; нет красной заливки или цвета ошибки. Подтвердите это по `screen.styles`; пустое окно показывает пустое состояние без артефактов.
5. Повторите после закрытия и повторного открытия проекта: breakpoint и Watches восстанавливаются из `.dsk`, если проект сохранён.

Для подсветки диагностик проверьте отдельный warning GCC: сразу после успешного Compile, до выбора элемента в **Compiler messages**, подтвердите фоновый цвет строки в `screen.styles`; измените эту строку и подтвердите возврат к обычному фону. Запишите сборку Scanline Term, версии GCC/GDB, команды, результат и наблюдаемые атрибуты. Не объявляйте UI-проверку пройденной по одному только успешному build или запуску `gdb_mi_self_check.exe`.

## Дополнительная проверка изменений

- Для изменений запуска, stdin/stdout, Ctrl+C/Ctrl+Break, смены экранного буфера или завершения процессов проверяйте **Run** и debuggee через Scanline Term MCP; при затрагивании совместимости повторяйте в Windows Terminal.
- Для изменений проекта проверяйте создание и открытие проекта в другой папке, `.dsk` рядом с `.prj`, повторное открытие, а также что несвязанные файлы проекта остаются нетронутыми.
- Перед commit запустите `git diff --check`, просмотрите `git status --short` и staged diff. Не добавляйте тестовые бинарники, `.obj`, пользовательские `.prj`/`.dsk`, резервные копии или содержимое `.build`.
- В итоговом сообщении отделяйте автоматические проверки от MCP UI-проверки и перечисляйте фактически проверенные терминальные хосты и сборки.
