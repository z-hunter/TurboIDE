# User Screen, shell и отладка: план реализации

Дата: 2026-10-01. Статус: реализация выполнена; локальная сборка и основные сценарии проверены.

## Цель и границы

Оставить один терминальный viewport с двумя сохраняемыми экранами: Turbo Vision IDE и настоящий консольный экран пользовательской программы. `Alt+F5` из IDE показывает User Screen; когда на нём нет работающей программы или shell, `Alt+F5` возвращает IDE. Во время обычного запуска и во время исполнения debuggee переключение в IDE не требуется. При остановке GDB IDE автоматически появляется, показывает текущую строку и значения переменных; `Alt+F5` позволяет посмотреть сохранённый вывод и вернуться к отладке. Настоящую `cmd.exe` можно запускать на User Screen до или после программы. Процесс shell живёт только пока открыт её сеанс: `exit` завершает его. Сохраняется экран, но не история и текущая директория shell между сеансами.

Одновременный показ полноэкранного вывода и окон IDE в одном viewport невозможен. На остановке пользователь переключается между ними. Не планируется переключение в IDE по `Alt+F5`, пока программа или shell выполняется; для прерывания зависшей программы нужен отдельный `Ctrl+Break`/`Ctrl+C` путь.

## Что уже есть

- `TurboIDEApp` владеет постоянными `ideScreenBuffer_` и `userScreenBuffer_`; Run и `Alt+F5` переиспользуют пользовательский экран.
- Run передаёт дочерней программе экранный буфер и общий консольный ввод, ждёт завершения, затем восстанавливает IDE. `Alt+F5` показывает сохранённый экран; Enter запускает `cmd.exe`, а `exit` закрывает shell-сеанс.
- Debugger запускает debuggee приостановленным с теми же handles, подключает GDB/MI по PID и затем продолжает выполнение. Так MI остаётся на отдельных pipes, а stdin/stdout программы идут через User Screen.
- Интегрированы GDB/MI: временная остановка на `main`, пользовательские breakpoints, continue, trace/step, остановка, текущий исходник/строка и окно Watches / Locals.
- GCC продолжает собирать отлаживаемый код с `-g -O0`. Путь к GDB задаётся `TURBOIDE_GDB` или находится в `PATH`.
- Status line упорядочена: `F1 Help`, `F7 Trace`, `F8 Step`, `F9 Make`, `F10 Menu`, `F11 Project`; F11 расположен у правого края.

## Результат реализации

Реализованы этапы 0–4: подтверждён запуск debuggee в общей консоли через `CREATE_SUSPENDED` и attach GDB по PID; постоянный User Screen; сеанс `cmd.exe`; остановки и шаги GDB/MI; маркеры breakpoint и текущей строки; окно Locals/Watches; соответствующие команды меню и клавиатуры.

Проверено локально: Release x64 собирается; `Alt+F5` до запуска открывает пользовательскую поверхность, Enter запускает shell, `exit` завершает её, повторный `Alt+F5` возвращает IDE; GDB останавливается на `main`/шаге, Locals показывает локальную переменную, а User Screen остаётся доступен на остановке. Сборка проекта выполнена повторно после закрытия только собственного тестового экземпляра IDE. Старый закреплённый процесс пользователя не затрагивался.

Остаются ручные проверки, которые зависят от интерактивного терминала: ввод через `scanf` во время отладки; Ctrl+Break/Ctrl+C в бесконечном цикле; crash/ошибки запуска и завершение IDE при активной отладке; Unicode и resize; совместимость Scanline Term, conhost и Windows Terminal. Эти пункты не считаются подтверждёнными текущей проверкой.

## Ожидаемое поведение

| Событие | Активный экран | Владелец ввода | Следующий переход |
| --- | --- | --- | --- |
| IDE без выполняемой программы | IDE | Turbo Vision | `Alt+F5` открывает User Screen |
| User Screen без процесса | User Screen | короткий цикл IDE | `Alt+F5` возвращает IDE; `Enter` запускает `cmd.exe` |
| `cmd.exe` работает | User Screen | shell | `exit` возвращает к User Screen без процесса |
| Обычный Run | User Screen | программа | exit/crash/прерывание возвращает IDE, вывод остаётся |
| Debug: программа выполняется | User Screen | debuggee | событие GDB `*stopped` возвращает IDE |
| Debug: breakpoint/step | IDE | Turbo Vision | строка и переменные обновлены; `Alt+F5` временно показывает вывод |
| Debug: resume/next/step | User Screen | debuggee | следующая остановка возвращает IDE |
| Debug: процесс завершился | IDE | Turbo Vision | `Alt+F5` показывает последнюю картину вывода |

Пока debuggee остановлен, User Screen только просматривается: shell на нём не запускается и клавиши не передаются debuggee. После `exit` shell оставляет свою картину в том же буфере; следующий Run дописывает или перерисовывает её согласно поведению самой программы. Очистку экрана пользователь может выполнить в shell командой `cls`.

## Этап 0. Доказать схему вывода отлаживаемой программы — выполнен

Это обязательный gate перед кодом окон отладки. Короткий изолированный прототип должен запустить GDB с `--interpreter=mi2` через отдельные pipe stdin/stdout/stderr, а debuggee — в той же консоли IDE с явными handles User Screen и `CONIN$`. Проверить два варианта по очереди:

1. GDB запускает inferior в общей консоли (`set new-console off`): определить, можно ли предоставить debuggee нужные handles, не направив её вывод и ввод в MI pipes. Не предполагать, что `set inferior-tty` решает это в MinGW Windows без проверки.
2. Если первый вариант не работает, IDE запускает debuggee с явными handles и останавливает его до пользовательского кода; GDB подключается по PID через MI (`-target-attach`), затем ставит breakpoint и продолжает выполнение. Отдельно доказать корректный порядок attach/resume для `CREATE_SUSPENDED` и остановку на `main` до первой пользовательской строки.

Проверочный C-код: `printf` до breakpoint, локальная переменная на breakpoint, `scanf` после continue, изменение курсора/цвета, нормальный exit. Успех: stdout/stderr и ввод остаются в User Screen; MI содержит только записи GDB; GDB останавливается и отдаёт locals; после stop рисунок User Screen не теряется. Если оба варианта не проходят, пересмотреть терминальную архитектуру до следующего этапа; не заменять вывод текстовым логом и не открывать внешнее окно как молчаливый fallback.

## Этап 1. Сделать User Screen постоянной поверхностью — выполнен

1. Владелец `userScreenBuffer_` — `TurboIDEApp`; создать его один раз при первом Run/`Alt+F5`, размер и начальные атрибуты взять у IDE. `runProgram` получает существующий handle и больше не создаёт/не закрывает его на каждый запуск. Старый экран сохраняется между запусками.
2. В `src/run.cpp` оставить запуск пользовательского EXE через `CreateProcessW` с явным путем и аргументами. Не прогонять команду Run через shell. На всех путях завершения вернуть активный IDE buffer и прежний режим `CONIN$`; сохранить код возврата и механизм остановки.
3. Заменить ожидание «любой клавиши» в `showUserScreen` на простой цикл с командами `Alt+F5` (назад) и `Enter` (запустить `cmd.exe`). Остальные клавиши не должны попадать в редактор. На User Screen без процесса вывести короткую подсказку без перерисовки пользовательского вывода, например в статусе IDE перед переключением или как отдельную временную строку, которая корректно восстанавливается.
4. Обрабатывать resize: размер обоих screen buffers должен следовать viewport; при уменьшении могут теряться обрезанные символы, это ограничение Windows buffer.

## Этап 2. Shell на User Screen — выполнен

1. Запускать системную `cmd.exe` через `CreateProcessW` напрямую, с User Screen в stdout/stderr и общим `CONIN$` в stdin. Начальная директория — настроенная working directory текущего проекта; без проекта — текущая директория IDE. Для первой версии выбрать `cmd.exe`; PowerShell оставить отдельным последующим выбором, если нужен.
2. Пока shell работает, IDE не читает `CONIN$` и не обрабатывает `Alt+F5`. После `exit` восстановить режим ввода и без очистки буфера показать User Screen в состоянии «без процесса»; оттуда `Alt+F5` возвращает IDE. Не оставлять живую shell, способную забирать клавиши IDE.
3. Повторный запуск shell создаёт новый процесс. Его `cd` и history не сохраняются между посещениями; это осознанный предел дешёвого варианта. Постоянная shell-сессия потребовала бы изоляции ввода, вероятно отдельного ConPTY, и не входит в текущий объём.
4. Ошибки запуска shell и отсутствие рабочего каталога показывать после возврата в IDE; ни один путь ошибки не должен оставлять User Screen активным.

## Этап 3. GDB/MI и связь с экраном — выполнен

1. Добавить узкий модуль `src/debugger.h/.cpp` для одного GDB-процесса. Он владеет MI pipes, токенами команд, PID debuggee и состояниями `idle`, `running`, `stopped`, `exited`. Читающий поток только складывает разобранные MI-события в очередь; Turbo Vision и screen buffers меняет только поток IDE.
2. При запуске Debug пересобрать программу с имеющимися `-g -O0`, передать arguments и working directory из проекта, открыть/сохранить User Screen. Способ запуска debuggee взять только из успешного этапа 0.
3. Поддержать `-break-insert`, `-exec-run` или `-target-attach` по выбранной схеме, `-exec-continue`, `-exec-step`, `-exec-next`, `-exec-interrupt`, `-stack-list-variables --simple-values` и `-data-evaluate-expression`. Обрабатывать `*running`, `*stopped`, exit и ошибки GDB; не делать выводов о состоянии по строке приглашения `(gdb)`.
   Пока User Screen активен, поток IDE ждёт сигнал очереди MI и событие прерывания в отдельном цикле; обычный цикл Turbo Vision возобновляется только после `*stopped` или exit. Пока IDE активна на breakpoint, её существующий `idle()` забирает события MI и обновляет окна. Никакой фоновый поток не вызывает методы Turbo Vision.
4. На `*stopped` сначала зафиксировать причину и frame, переключить активный buffer на IDE, открыть нужный исходник, подсветить исполняемую строку, затем запросить и показать локальные переменные и Watches. Если файл или символ не найден, оставить сессию управляемой и показать конкретную диагностику.
5. На continue/step переключить активный buffer на User Screen до возобновления debuggee; когда выполнение снова остановится, вернуть IDE. Если шаг остановился без видимого вывода, краткое переключение всё равно допустимо, но не должно очищать экран.
6. Пока debuggee остановлен, `Alt+F5` показывает снимок реального User Screen и возвращает IDE по `Alt+F5`; переменные и текущая строка остаются доступны в IDE. При выполнении программы клавиатура принадлежит debuggee. Ввод `scanf` должен работать так же, как в обычном Run.
7. `Ctrl+Break` во время выполнения запросит остановку через GDB; если GDB/debuggee не отвечают, обеспечить явную команду завершения с ограниченным ожиданием и восстановлением IDE. Не завершать чужие процессы. При закрытии IDE корректно закрыть GDB, debuggee и handles.

Проверка этапа 0 должна также выяснить, получает ли IDE `Ctrl+Break`, когда debuggee владеет вводом. Способ остановки и аварийного завершения зависит от этого результата; нельзя считать рабочим путь обычного Run автоматически применимым к GDB.

## Этап 4. Окна и команды отладки — выполнен

- В редакторе: маркер breakpoint и отдельный маркер текущей исполняемой строки; они должны сосуществовать с подсветкой синтаксиса и сообщениями компилятора.
- В меню Debug: Start/Continue, Step Into (`F7`), Step Over (`F8`), Toggle Breakpoint, Stop/Reset (`Ctrl+F2`); разрешённость команд зависит от состояния GDB. Существующие сочетания из `TECHNICAL_PLAN.md` сохранять, если нет конфликта.
- Окно Watches/Locals: имя, значение, недоступное значение с понятным объяснением; обновление только на остановке. На продолжении не показывать старые значения как актуальные.
- При завершении или аварии: причина и exit code в Messages/статусе, IDE активна, User Screen доступен через `Alt+F5`; маркер текущей строки снимается.

## Приёмка и матрица проверок

Ручные проверки в Scanline Term (основной хост), затем conhost и Windows Terminal:

1. `Alt+F5` до первого Run открывает User Screen; `Enter` запускает `cmd`; команды `echo`, `cd`, Unicode-текст и `exit` работают; `Alt+F5` возвращает IDE; shell не перехватывает последующие клавиши редактора.
2. `Ctrl+F9` запускает обычную программу с `printf`, `scanf`, цветом и позиционированием курсора. После выхода IDE появляется, `Alt+F5` показывает точный экран; повторный запуск не уничтожает buffer до начала вывода новой программы.
3. Debug: breakpoint после нескольких строк вывода показывает в IDE текущую строку и корректные locals; `Alt+F5` показывает эти строки вывода без сообщений MI; возврат и `F7/F8` сохраняют значения и экран.
4. Debug: после continue программа запрашивает stdin, ввод принимается User Screen; следующий breakpoint снова показывает изменённые значения. Проверить break в другом файле проекта, Watches, normal exit и crash.
5. `Ctrl+Break` при бесконечном цикле, ошибки запуска GDB/debuggee/shell, закрытие IDE, изменение размера viewport и возврат из каждого состояния восстанавливают ввод и экран IDE.

## Оценка и порядок работы

| Работа | Оценка одного разработчика | Gate |
| --- | ---: | --- |
| Этап 0: доказать разделение GDB MI и console I/O | 1–2 дня | Нужна демонстрация breakpoint + вывод + stdin в одном viewport |
| Этап 1: сохраняемый User Screen и управление Alt+F5 | 1–2 дня | После Run экран сохраняется, ввод IDE не ломается |
| Этап 2: сеанс `cmd.exe` | 1 день | `exit` и возврат безопасны |
| Этапы 3–4: GDB/MI, остановки, строки, переменные, команды | 5–8 дней | Сценарии debug проходят в основном терминале |
| Ручная проверка хостов и исправление совместимости | 1–2 дня | Scanline Term, conhost, Windows Terminal |

Итого ориентировочно 9–15 инженерных дней. Оценка условна до этапа 0: именно разделение консольного ввода/вывода GDB и debuggee определяет сложность. Каждую стадию завершать работающим состоянием существующих `Ctrl+F9` и `Alt+F5`.
