# TurboIDE: исследование и технический план

Дата: 2026-10-01. Цель: нативная консольная Windows IDE с рабочим процессом и обликом Borland Turbo C / Borland C++, для разработки **обычных Win32 C-программ**. Основной компилятор пользовательского кода — MinGW-w64 GCC x64; TCC 0.9.27 не обеспечивает просмотр локальных переменных в GDB. Приоритеты заказчика: интерфейс и процесс работы BC; в первой версии отладка с точками останова, шагами и переменными. Старые DOS-программы без изменений не входят в критерий совместимости.

## Проверенные исходные условия

- Рабочая папка `C:\Dev.dir\projects.dat\TurboIDE` пока не содержит исходников и не является Git-репозиторием. `codex-doctor -Fast` подтвердил доступность локальных инструментов, но сообщил об отсутствии `AGENTS.md` и Git; текст политики агента был передан в разговоре.
- `C:\Dev.dir\Tcc\tcc.exe` — TCC 0.9.27, x64 Windows. Рядом есть `i386-win32-tcc.exe`, заголовки, библиотеки и `libtcc.dll`. `tcc.exe -h` предлагает `-g`, но документация этой установленной версии описывает его как сведения для трассировки ошибок времени выполнения. [Документация TCC](https://github.com/TinyCC/tinycc/blob/mob/tcc-doc.texi).
- Локально доступны CMake и MSVC `cl.exe`. Сравнивались установленный GCC 5.3/GDB 7.6 (32-битные) и переносимый [w64devkit 2.10.0](https://github.com/skeeto/w64devkit): GCC 16.2.0 x64 + GDB 17.2. Второй комплект на PE x64 с `-g -O0` показывает точки останова, шаги и локальные значения. GDB/MI вернул `value=41`, после `-exec-next` — `value=42`. Отладка и аргументы запуска с Unicode-именем исходника работают в короткой пробе, хотя GDB выводит имя в текущей системной кодировке; абсолютный Unicode-путь выходного EXE ломает linker w64devkit, поэтому выходной путь должен оставаться ASCII.
- Установленный TCC 0.9.27 x64 с актуальным GDB 17.2 останавливается на строке, но `info locals` отвечает `No locals`, `print value` — `No symbol`. Короткая проба `tcc -gdwarf` всё равно создала `.stab`/`.stabstr`. Локальный 32-битный GDB также не открывает x64 PE. Текущий TCC остаётся вне v1: отладка через GCC значительно проще и работает на x64.
- Современный [Turbo Vision](https://github.com/magiblot/tvision) предоставляет окна, меню, диалоги, `TEditor`, Unicode, поддержку Windows Console API и [системный буфер обмена](https://github.com/magiblot/tvision#clipboard-interaction). Проект собирается CMake с MSVC или MinGW; библиотека требует C++14, поэтому IDE пишется на C++17/MSVC, а пользовательский C — MinGW-w64 GCC. В Windows версия работает через Win32 Console API; совместимость с каждым эмулятором терминала надо проверить. Встроенная интеграция буфера требует команд `cmCut/cmCopy/cmPaste` и проверки `TClipboard` на всех нужных полях. [README Turbo Vision](https://github.com/magiblot/tvision#features).
- У Turbo Vision — исходный текст Borland с отдельным уведомлением и MIT для последующих изменений; GCC/GDB — отдельные пользовательские инструменты, не включать их бинарники в IDE. Сохранять `COPYRIGHT`/лицензионные файлы Turbo Vision при распространении. [Turbo Vision COPYRIGHT](https://github.com/magiblot/tvision/blob/master/COPYRIGHT), [w64devkit](https://github.com/skeeto/w64devkit).

## Результат первой версии

Один `turboide.exe`, запускаемый в Windows Console Host и Windows Terminal. Синий рабочий стол, строка меню и состояния, перекрывающиеся окна исходников и сообщений, мышь и клавиатура, классические команды. IDE открывает/сохраняет UTF-8 C-файлы, умеет работать с одним файлом без проекта и с проектом из нескольких `.c`, собирает GCC, открывает ошибку на нужной строке, запускает интерактивную консольную программу и возвращает её экран для просмотра. Отладчик показывает текущее место, поддерживает breakpoint/continue/step into/step over/stop и вычисление выражения или локальных переменных.

Начальные горячие клавиши: `F2` Save, `F3` Open, `Alt+F9` Compile, `F9` Make, `Ctrl+F9` Run, `Alt+F5` User Screen, `F7` Trace Into, `F8` Step Over, `Ctrl+F2` Reset; меню дублирует каждую команду. Точные спорные сочетания сверить с выбранной версией BC при визуальном проходе; не блокировать на этом основу.

GCC поддерживает C и доступные Win32 API, но это не Borland `graphics.h`, BGI, DOS-прерывания, 16-битные указатели или Borland C++ ABI. Сохранение интерфейсного облика не создаёт совместимости старых бинарников и заголовков. Поддержка `graphics.h`, DOS-эмуляция, язык C++, встроенный терминальный эмулятор и собственный движок отладки потребовали бы отдельных проектов.

## Архитектура с минимальным количеством деталей

```text
TurboIDE.exe (C++17, MSVC, Turbo Vision)
  ├─ TApplication: меню, статус, редактор, ошибки, окна отладки
  ├─ Project: текущий .c или простой .prj со списком .c и аргументами
  ├─ Build: CreateProcessW → gcc.exe → диагностика → переход к строке
  ├─ Run: CreateProcessW → экран/ввод дочерней консольной программы
  └─ Debug: процесс GDB --interpreter=mi2/mi3 → PE с символами
                         └─ отлаживаемая консольная программа
```

- Никакого shell для путей и пользовательских аргументов: запуск через `CreateProcessW` с явным исполняемым файлом и корректно закодированной командной строкой. Текущая директория процесса — директория проекта. Флаги компиляции передавать отдельными аргументами; сборочный вывод читать асинхронно, чтобы интерфейс не замирал. Сохранять все изменённые исходники перед сборкой после подтверждения пользователя.
- Для одиночного файла проектный формат не нужен. Для нескольких файлов достаточно UTF-8 `.prj` с повторяемыми строками `source=...`, `include=...`, `define=...`, `library=...`, `arg=...`; пути относительно файла проекта. Один проход парсера, ошибки с номером строки. Не добавлять JSON-библиотеку и универсальную систему сборки.
- Редактор: использовать `TEditor`/`TFileEditor` и имеющиеся диалоги Turbo Vision. Проверить поиск/замену, штатный однократный Undo, выделение, сохранение UTF-8, CRLF/LF, имён файлов Unicode и больших вставок; тонкий код IDE отвечает за список документов, заголовки, переход к строке и несохранённые изменения. Встроенного Redo у `TEditor` нет. Системный clipboard подключить через штатные `cmCut/cmCopy/cmPaste`/`TClipboard`.
- Экран программы нельзя заменить захватом `stdout`: это ломает `scanf`, `conio` и произвольные курсорные операции. Короткая проба подтвердила, что Win32 `CreateConsoleScreenBuffer`/`SetConsoleActiveScreenBuffer` переключает отдельный экран и обратно в тестовой псевдоконсоли. В v1 использовать отдельный сохраняемый buffer для IDE и программы; ввод временно передаётся дочернему процессу, после завершения/ошибки/остановки восстановить IDE, `Alt+F5` повторно показывает экран программы. Прямой запуск Tvision `hello.exe` под ConPTY тоже прошёл и восстановил консоль после Alt-X. Ручная проверка Windows Terminal ещё нужна. Для debuggee GDB умеет `set new-console on`, подтверждено через MI. [Windows screen buffers](https://learn.microsoft.com/en-us/windows/console/console-screen-buffers), [Microsoft: совместное использование консоли](https://learn.microsoft.com/en-us/windows/console/creation-of-a-console).
- Отладчик: использовать [GDB/MI](https://sourceware.org/gdb/current/onlinedocs/gdb.html/GDB_002fMI.html), а не разбирать интерактивный текст GDB. Один процесс GDB, команды с токенами и обработка асинхронных `*stopped`/`=...` событий; `-break-insert`, `-exec-run`, `-exec-next`, `-exec-step`, `-exec-continue`, `-stack-list-variables`/`-data-evaluate-expression`, `-gdb-exit`. Стандартный вывод и ввод отлаживаемого процесса не должны попадать в управляющий канал MI. На Windows GDB поддерживает [отдельную консоль для debuggee](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Cygwin-Native.html); это первый способ отделить экран программы в режиме отладки, прежде чем пытаться встроить его в IDE.
- Unicode разделить на четыре независимые гарантии: UTF-8 в UI/редакторе; Unicode имена файлов IDE (`W`-варианты Win32); приём GCC/GDB путей с Unicode; вывод самой пользовательской программы. GCC компилировал исходник с Unicode-именем при ASCII-имени выходного EXE. Не задавать GCC абсолютный Unicode путь выходного файла: linker не смог открыть его в этой среде. Артефакты собирать по относительному ASCII-пути в project build directory. Вывод пользовательской C-программы зависит и от кода программы, и от её локали/кодовой страницы; IDE не может автоматически превратить `printf` произвольной кодировки в Unicode.

## Зафиксированное решение по отладке

Отладочная цепочка проверена на маленьком многострочном x64 C-примере. Выбраны GCC и GDB из w64devkit 2.10.0; приложение запускает GDB в режиме MI, строит пользовательскую программу с `-g -O0`, а Run/обычная сборка используют тот же GCC.

- Контрольные результаты: GDB/MI сообщает `*stopped,reason="breakpoint-hit"`; `-stack-list-variables --simple-values` вернул локальный `value=41`; после `-exec-next` вернул `value=42`; `-gdb-exit` закрыл сессию. `set new-console on` принимается GDB и отражается в MI. Функциональность TCC 0.9.27 с GDB 17.2 не проходит контроль locals, поэтому откладывается.
- GCC/GDB распространять или устанавливать отдельно от IDE; не класть 742 MB распакованного toolchain в репозиторий. В конфигурации IDE указывать путь к `gcc.exe` и `gdb.exe`; версию toolchain закрепить в инструкции. Не собирать Debug другим компилятором, чтобы Run/Debug имели одинаковые семантику и ABI.

## Матрица приёмки и границы

- Windows Console Host и Windows Terminal: запуск, ресайз, клавиатура, мышь, возврат параметров консоли после нормального выхода и аварии.
- UTF-8 исходники: кириллица и CJK в комментариях/строках; пути с пробелами и кириллицей; CRLF/LF; copy/paste с приложением Windows. GCC принял исходник с Unicode путём и создал исполняемый файл в build-папке по относительному ASCII-пути. Полный многофайловый Unicode путь вместе с GDB остаётся в ручной проверке.
- Сборка: один файл, два модуля, заголовок, ошибка компиляции, код завершения, отсутствие EXE при ошибке. Никакого запуска старого EXE после неуспешной сборки.
- Run: ввод, вывод, цвет/курсор, длинный вывод, завершение с ненулевым кодом, остановка по пользователю; возврат ввода редактору.
- Debug: breakpoint, continue, step into/over, локальная и глобальная переменная, вычисление простого выражения, завершение, debuggee с `scanf`, корректная очистка дочерних процессов.
- За пределами v1: реальный 16-битный DOS, BGI, исходная Borland RTL, C++, watchpoints, память/регистры/дизассемблер, профилировщик, компиляция без сохранения исходника, плагины и собственный терминальный эмулятор. Их добавлять только после отдельного требования.
