# Stage 4b — стабилизация отладки и проверка пользовательского экрана

## Цель

Довести уже работающие сборку, запуск, User Screen и базовую отладку до предсказуемого состояния: IDE должна корректно принимать ввод программы, останавливать и завершать отладчик, показывать локальные переменные и Watches, а также сохранять точки останова и Watches в desktop-файле проекта.

## Текущее состояние

- IDE собирает проекты GCC, показывает сообщения компилятора, запускает программу и предоставляет User Screen с возможностью перейти в shell.
- Реализована базовая GDB-отладка: точки останова, шаги, текущая строка и локальные переменные.
- Пользователь проверил обычный запуск программы, переключение User Screen и вход в shell.
- До принятия этапа остаётся проверить ввод отлаживаемой программы, прерывание зависшего процесса, завершение дочерних процессов, Unicode и работу в разных хостах терминала.
- Окно Watches/Locals сейчас показывает только локальные переменные.
- README содержит устаревшее описание хоткеев: F11 указан неверно для Messages; фактическая привязка — F11 для Project и Shift+F11 для Messages.
- Часть документации описывает GDB как будущую работу, хотя базовая интеграция уже есть. Нужно отделить реализованное от проверенного и принятого.
- Последняя попытка сборки Release остановилась в MSBuild до диагностики C++ из-за дублирующихся записей PATH/Path в окружении.

## Решения по формату сессии

- Использовать `.dsk` рядом с соответствующим `.prj`, как desktop-файл конкретного проекта.
- Сохранять в `.dsk` расположение открытых окон, точки останова и выражения Watches.
- Не мигрировать автоматически неоднозначные `.dsk` из текущей директории: неясно, к какому проекту они относятся.
- Не удалять старые `.dsk`; сохранять совместимость с уже поддерживаемыми записями.
- Если проект не открыт, точки останова и Watches могут жить только до завершения текущей сессии.
- Сохранять изменения desktop сразу при изменении списка точек останова или Watches.

## План работ

### 1. Исправить и актуализировать документацию

- В README уточнить компилятор и способ сборки, запуск IDE, клавиши Run/Debug, User Screen и shell.
- Исправить хоткеи Project и Messages.
- Описать связь `.prj` и `.dsk`, а также расположение desktop-файла.
- В `TECHNICAL_PLAN.md` и `USER_SCREEN_DEBUG_PLAN.md` пометить, что реализовано в коде, а что проверено пользователем или ещё требует проверки.
- Сохранить прежние отчёты как исторические; добавить отчёт этого этапа после завершения.

### 2. Укрепить жизненный цикл отладки

- Проверить полный путь создания GDB и debuggee, включая ошибки запуска и закрытие IDE.
- Везде ограничить ожидание ответа отладчика разумным timeout; зависший GDB должен приводить к понятной ошибке, а не к вечной блокировке интерфейса.
- Команда Stop должна завершать только процессы GDB/debuggee, созданные этой IDE.
- При любом выходе восстановить экран IDE, ввод и состояние клавиатуры.
- Сохранять причину `*stopped` и код завершения; показывать отдельно нормальный выход, ненулевой код, завершение сигналом и остановку на breakpoint.
- Проверить архитектуру запуска: debuggee создаётся приостановленным (`CREATE_SUSPENDED`), затем GDB подключается к нему. Документация должна соответствовать реальному коду.
- Если исходный файл или строка недоступны, показать ошибку и оставить сессию отладки управляемой.

### 3. Разделить Locals и Watches

- Добавить Watches в Debug: Add Watch (`Ctrl+F7`), Evaluate (`Ctrl+F4`), Delete выбранного Watch (`Del`).
- Не смешивать выражения Watches со списком локальных переменных.
- Обновлять значения при остановленном debuggee; ошибку одного выражения показывать рядом с ним, не обрывая всю сессию.
- Для вычисления использовать GDB/MI `-data-evaluate-expression`.
- Запретить вызовы функций при вычислении Watches, чтобы просмотр значения не менял состояние программы.
- Во время вычисления временно запретить запись в память и регистры и восстановить прежний режим после команды.

GDB предупреждает, что вычисление выражений может вызывать функции и менять состояние программы. Поэтому Watches должны оставаться наблюдательными. Ссылки: [GDB/MI Data Manipulation](https://sourceware.org/gdb/current/onlinedocs/gdb.html/GDB_002fMI-Data-Manipulation.html), [GDB Observer Mode](https://www.sourceware.org/gdb/current/onlinedocs/gdb.html/Observer-Mode.html).

### 4. Сохранять Breakpoints и Watches в `.dsk`

- Добавить повторяющиеся текстовые записи для breakpoint и watch expression в уже используемый `.dsk`.
- Загружать их при открытии проекта и сохранять сразу после добавления, удаления или изменения.
- Оставить прежние записи сессии читаемыми; неизвестные записи игнорировать безопасно.
- Не переносить точки останова и Watches из неоднозначных файлов в текущей директории автоматически.

### 5. Проверить разбор GDB/MI

- Убедиться, что парсер выдерживает вложенные структуры и экранированные строки, используемые GDB для locals и Watches.
- Добавить один небольшой fixture/self-check для вложенных и экранированных MI-значений.
- Проверить поведение при ошибке конкретного выражения, отсутствии исходного файла и завершении debuggee.

## Проверка и критерии приёмки

Сначала собрать чистую конфигурацию Release в исправленном окружении MSBuild. Не завершать процессы пользователя ради освобождения файлов.

Затем вручную проверить:

1. Scanline Term, conhost и Windows Terminal: запуск программы, переключение User Screen и возврат в IDE.
2. Отладку небольшой C-программы с `printf`, `scanf`/`fgets`, Unicode и несколькими исходными файлами.
3. Breakpoint, F7/F8/F4, текущую строку, Locals, добавление/удаление Watch и ошибку вычисления выражения.
4. Сохранение и восстановление окон, Breakpoints и Watches после перезапуска проекта.
5. Ctrl+C/Ctrl+Break на бесконечном цикле; нормальный выход, ненулевой код, аварийное завершение, отсутствие GDB и закрытие IDE во время отладки.
6. Отсутствие оставшихся дочерних процессов и восстановление ввода/экрана IDE после каждого сценария.
7. Подсказку User Screen: она не должна навсегда портить нижнюю строку программы или shell.

Этап принимается после успешной сборки и прохождения сценариев остановки/очистки, ввода программы, Watches и сохранения desktop. Различия между терминальными хостами фиксируются отдельно, если зависят от их возможностей.

## Ограничения и риски

- Поведение ввода и прерывания зависит от связки Windows, ConPTY и конкретного терминального хоста; один успешный хост не подтверждает остальные.
- Оценка: примерно 5–8 инженерных дней, включая ручную проверку трёх хостов. Если среда сборки или терминальные хосты недоступны, это фиксируется как непроверенная часть, а не как пройденный сценарий.
